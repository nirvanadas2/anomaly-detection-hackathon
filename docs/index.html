the assignment

Behavioral anomaly detection, from raw logs to a risk score

Build an AI-powered behavioral anomaly detection system for cybersecurity access logs. Model "normal" access behavior per user, service account, and device — then detect and classify anomalies in near real-time, surfacing each one with an explainable risk score an analyst can actually act on.
CONSTRAINT 01

Sequential data

Access events are ordered per-entity time series, not i.i.d. rows — behavior only makes sense in context.

CONSTRAINT 02

Extreme class imbalance

Anomalies are ~1% of events. A model that predicts "normal" for everything scores deceptively well.

CONSTRAINT 03

Concept drift

Legitimate behavior shifts over weeks — new responsibilities, new resources — and shouldn't trip alerts.

CONSTRAINT 04

Explainability

A bare risk score isn't actionable. Every alert needs a human-readable reason it fired.

CONSTRAINT 05

Cold start

New entities have no history yet a baseline is still needed from day one.

traffic light system

Every alert gets a light

Every view in the dashboard — and every panel on this page — uses the same three colors to mean the same three things. Every login gets a light. Most stay green. A few need a second look.

Green light

Baseline behavior consistent with this entity's learned profile — typical resources, hours, devices, and locations. No action needed.

Yellow light

Flagged: risk score in the top alert budget, or a rule matched — worth an analyst's attention, not yet a confirmed incident.

Red light

Critical: classified against a specific attack pattern with an explanation — a confirmed anomaly type, ready to escalate.

how it works

Four stages, one event at a time

01

Ingest

Access events stream in per entity — user, service account, or device — preserving sequence order.

02

Score

An unsupervised LSTM autoencoder over sliding event windows produces a reconstruction-error risk score, backed by a cold-start baseline and rolling drift recalibration.

03

Classify

The top slice of risk_score events run through six rule-based checks, each independently deciding whether — and which — attack pattern matched.

04

Explain

Every alert carries a plain-language explanation string: which features fired, what threshold was crossed, and why.

what it catches

Six classified attack patterns

Each rule looks only at an entity's own history at or before its timestamp — no future knowledge, no peeking across entities except where the pattern itself is inherently cross-entity.

AUTH

Brute force

A burst of failed auth attempts from one source_ip against one entity within a short window — worse if that IP has never been seen for this entity before.

AUTH

Credential stuffing

The cross-entity signature: many different entities, mostly failing auth, hit from a small cluster of related source IPs in the same window.

IDENTITY

Credential misuse

A login that's novel on every axis at once — new device, new geo_location, and an off-hours timestamp this entity almost never uses — evaluated jointly, not separately.

DEVICE

Device spoofing

Access claiming an established identity but arriving from device or fingerprint characteristics that don't match this entity's known device history.

GEO

Impossible travel

Geo-velocity between two consecutive events for the same entity exceeds any plausible travel speed — compounded if the device fingerprint changed too.

MOVEMENT

Lateral movement

A short-window chain of resources outside the entity's normal set, escalating toward progressively rarer, higher-value resources.

what's next

Roadmap & known limitations

  • Incident-level grouping

    Scoring is currently per-event — a single attack chain can surface as several separate flags, and some individual events in a chain go unclassified even when the overall incident is caught.

  • Low-and-slow exfiltration detection

    Not yet built. Current rules are tuned for bursty, short-window behavior; a slow drip of access spread over days needs a different detection strategy.

  • Insider drift tuning

    The concept-drift stress test holds up well (92% correctly read as normal) but the remaining edge cases — genuine first-ever access to a newly available resource — could use tighter tuning.

  • Analyst feedback loop

    Alert dispositions (confirmed / false positive) aren't fed back into scoring or thresholds yet — a natural next step for reducing the alert-queue false positive rate over time.

  • Cross-entity correlation graph

    Detections are per-entity today. Correlating flagged events across entities could surface coordinated or multi-account incidents that no single entity's history would reveal alone.

  • Production streaming via Kafka

    The real-time feasibility demo replays a static CSV as a live feed; a production deployment would sit behind an actual streaming ingestion layer.
